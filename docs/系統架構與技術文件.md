## 2. 整體架構

採分層架構（Layered Architecture），單向資料流：

```
UI (Compose)  ──►  ViewModel (Hilt)  ──►  Repository  ──►  Room / DataStore
                                              │
                                              └►  Remote (Retrofit / OkHttp SSE)  ──►  LLM API
```

- **UI 層**：Compose 畫面，狀態由 `StateFlow` 暴露，以 `collectAsStateWithLifecycle()` 訂閱。
- **ViewModel 層**：持有畫面狀態與商業流程，透過 Hilt 注入 Repository。
- **Repository 層**：整合本機儲存與遠端呼叫，對上提供乾淨 API。
- **Data 層**：Room（結構化資料）、DataStore（偏好設定）、Retrofit/OkHttp（遠端）。

設計原則：

- 單一 `app` module，套件以功能分層，避免過度工程。
- 畫面狀態以不可變資料類別（`@Immutable`）表示。
- 對話與訊息透過 Room `Flow` 即時更新，UI 被動訂閱。

## 4. 資料流

### 4.1 應用程式啟動

1. `LlmChatApp`（`@HiltAndroidApp`）初始化 Hilt 容器。
2. `MainActivity` 建立 Compose 內容，讀取 `AppSettingsViewModel` 的顯示模式 / 字型 / TTS 語言。
3. 依 `screenWidthDp >= 600` 決定精簡（`NavigationBar`）或展開（`NavigationRail`）導航。
4. `NavHost` 起始目的地為 `CONVERSATIONS`。

### 4.2 聊天流程

```
使用者送出
  └─► ChatViewModel.send()
        ├─ 取得使用中 Profile（或對話既有 Profile）
        ├─ 必要欄位驗證（Base URL / 模型）
        ├─ 若為草稿對話 → 建立對話、開始 observeMessages
        ├─ 讀取歷史 → ChatMessageDto 清單
        ├─ ContextBuilder.build()（裁剪至 token 預算）
        ├─ 寫入使用者訊息 → 必要時以首句命名對話
        ├─ ChatRepository.stream() ──► ChatStreamClient（SSE）
        │     ├─ Delta        → 累積並更新 UI（節流 50ms）
        │     ├─ Reasoning    → 累積思考內容
        │     ├─ Completed    → 記錄 finish_reason
        │     └─ Failed       → 顯示錯誤
        └─ finally（NonCancellable）
              ├─ 有內容 → 寫入助理訊息（+ 必要時自動朗讀）
              ├─ 空回覆 → 依 finish_reason 顯示中文提示
              └─ 清除串流狀態
```

## 5. 資料模型與持久化

### 5.1 Room 資料表

| 表 | 欄位 |
| --- | --- |
| `profiles` | id, name, baseUrl, model, systemPrompt, temperature, maxTokens, contextWindow, thinkingMode, reasoningEffort, createdAt |
| `conversations` | id, profileId(FK), title, createdAt, updatedAt |
| `messages` | id, conversationId(FK), role, content, createdAt |

- 外鍵設為 `CASCADE`：刪除 Profile 會連帶刪除其對話；刪除對話會連帶刪除其訊息。
- 資料庫版本 **v2**（含 `MIGRATION_1_2`，保留既有資料；新增 `thinkingMode` 與 `reasoningEffort` 欄位）。
- 資料庫檔名：`llmchat.db`。

### 5.2 DataStore（`settings`）

| 鍵 | 型別 | 用途 |
| --- | --- | --- |
| `current_profile_id` | Long | 目前使用中的設定檔 id（-1 表示無） |
| `debug_log_enabled` | Boolean | 是否啟用除錯記錄 |
| `theme_mode` | String | 顯示模式（`ThemeMode`） |
| `chat_font_size` | Float | 聊天字型大小（sp） |
| `always_read` | Boolean | 是否總是朗讀 |
| `tts_language` | String | 朗讀語言（`TtsLanguage`） |

### 5.3 領域模型

- `Profile`：連線設定，含 `ThinkingMode`、`ReasoningEffort` 列舉。
- `Conversation` / `Message` / `ChatRole`（USER / ASSISTANT / SYSTEM）。
- `ThemeMode`（SYSTEM / LIGHT / DARK）、`TtsLanguage`（SYSTEM / ZH / EN）。

## 6. 網路層與串流

### 6.1 Retrofit 服務（`OpenAiApiService`）

| 方法 | 端點 | 用途 |
| --- | --- | --- |
| `listModels` | `GET models` | 測試連線、列舉可用模型 id |
| `chatCompletion` | `POST chat/completions` | 非串流後備呼叫 |

### 6.2 SSE 串流（`ChatStreamClient`）

- 使用 `okhttp-sse` 的 `EventSource` 對 `POST {baseUrl}/chat/completions` 發出 `stream = true` 請求。
- 以 `callbackFlow` 包裝，對外提供 `Flow<StreamEvent>`。
- 事件型別：
  - `Delta`：增量文字。
  - `Reasoning`：DeepSeek `reasoning_content` 思考內容。
  - `Completed`：附帶 `finish_reason`。
  - `Failed`：附帶 HTTP 狀態與伺服器錯誤內容。
- **結束判定**：收到 `data: [DONE]` **或** 帶 `finish_reason` 的分塊即結束（部分供應商只送後者）。
- **逾時**：連線 30s、寫入 30s、讀取（閒置）120s。

### 6.3 JSON 設定（`AppModule.provideJson`）

```kotlin
Json {
    ignoreUnknownKeys = true
    isLenient = true
    explicitNulls = false
    coerceInputValues = true
}
```

- 串流分塊為部分資料（可能只有 `role`、只有 `content`、或僅 `finish_reason`），DTO 欄位皆為可空並附預設值，避免解碼失敗。

## 7. 上下文管理

LLM API 無狀態，每次請求需送出**裁剪後**的訊息子集；完整歷史永遠保存在本機。

### 7.1 Token 估算（`TokenEstimator`）

零依賴啟發式估算：

- 中日韓字元（CJK / 假名 / 諺文 / 全形）約 **1 token / 字**。
- 其他字元約 **4 字元 / token**（無條件進位）。
- 每則訊息另加固定 overhead（4 tokens）。

### 7.2 預算與裁剪（`ContextConfig` / `ContextBuilder`）

- 輸入預算 = `Context Window` − 保留輸出 − 5% 安全邊界（下限 256 tokens）。
- 保留輸出 = `maxTokens`（>0）或預設 2048。
- 裁剪策略：
  1. 從**最舊的非 system 訊息**開始丟棄，直到符合預算。
  2. 對齊到 `user` 訊息邊界（避免歷史以 assistant 開頭）。
  3. **System Prompt 永不裁剪**。
- 僅裁剪送給 API 的子集，資料庫內容不受影響。

## 8. 安全性

- **API Key 加密**：以 `EncryptedSharedPreferences`（Android Keystore）加密儲存，不明文落盤、不寫入記錄。
- **除錯記錄不含金鑰**：送出的請求 body 記錄時不含 `Authorization`。
- **備份**：`android:allowBackup="false"`，避免敏感資料被備份外流。
- **明文 HTTP**：透過 `network_security_config.xml` 允許 cleartext，以支援自架服務；請僅使用可信任端點。

## 10. 穩健性與相容性

- **非串流後備**：若伺服器忽略 `stream=true` 而未回任何串流內容且未失敗，自動改用一次非串流請求。
- **自動重試**：`/models`、非串流後備，以及「尚未收到任何內容」的串流連線，遇 `IOException` 或 429/5xx 會以指數退避最多重試 3 次。
- **串流結束判定**：見 [6.2](#62-sse-串流chatstreamclient)。
- **逾時**：串流閒置逾時 120 秒，避免連線卡死。
- **空回覆提示**：若最終無內容，依 `finish_reason` 顯示中文提示（`length` / `content_filter` / `tool_calls` 等）。
- **參數清理**：送出前將 `temperature` 四捨五入至 2 位。
- **相容其他端點**：`thinking` 欄位僅在使用者明確設定時才送出，維持對一般 OpenAI 相容服務的相容性。
- **UI 節流**：串流期間每 50ms 才更新一次畫面，降低 Compose 重組壓力。
- **TTS 延後初始化**：`SpeechController` 的 `TextToSpeech` 引擎於**首次朗讀時**才建立（`ensureEngine()`），避免進入聊天頁時在主執行緒進行系統服務綁定。
- **單次載入對話**：開啟既有對話時於同一協程讀取 `getConversation` 與 `getMessages`，並以 `CHAT` 路由的可選 `title` 參數帶入標題，讓標題與內容同步出現、避免載入閃爍。
